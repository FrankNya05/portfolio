## 4. Architecture technique du formulaire

### Flux complet d'un message

```
Visiteur remplit le formulaire (nom, email, sujet, message)
        ↓
ContactForm.tsx (côté client / navigateur)
Envoie une requête HTTP POST vers /api/contact avec les données en JSON
        ↓
src/app/api/contact/route.ts (côté serveur / Node.js)
1. Vérifie le rate limiting (IP)
2. Vérifie le honeypot
3. Valide et sanitize tous les champs
4. Charge les credentials depuis .env.local
5. Nodemailer se connecte à Gmail via SMTP
6. Gmail envoie l'email
7. Renvoie { success: true } au navigateur
        ↓
ContactForm.tsx affiche l'état "success" ou "error"
        ↓
Frank reçoit l'email dans franknya.eng@gmail.com
Le champ replyTo est l'email du visiteur → Frank peut répondre directement
```

### Mesures de sécurité implémentées

| Mesure | Détail |
|---|---|
| **Secrets dans .env.local** | Jamais dans le code source, jamais sur GitHub |
| **Rate limiting** | 3 requêtes max par IP par tranche de 10 minutes (in-memory Map) |
| **Honeypot** | Champ invisible — bots le remplissent, soumission ignorée silencieusement |
| **POST uniquement** | La route rejette GET et toute autre méthode (405) |
| **Validation serveur** | Tous les champs validés côté serveur, indépendamment du client |
| **Longueurs max** | name ≤ 100 · email ≤ 200 · subject ≤ 200 · message ≤ 5000 |
| **Sanitization** | Suppression des `\r\n` pour prévenir l'email header injection |
| **Validation email** | Regex côté serveur pour vérifier le format |
| **Env validation** | Si une variable manque, la route renvoie une erreur 500 claire |

**Note sur le rate limiting en serverless :** le store in-memory fonctionne correctement sur un serveur classique. Sur Vercel (serverless), il ne persiste pas entre les cold starts mais reste efficace sur les warm starts. Suffisant pour un portfolio — si le trafic augmente, une upgrade vers Upstash Redis est simple.

## 5. Concepts expliqués pendant la session

### Client vs Serveur dans Next.js

Même en développement local (`npm run dev`), deux environnements distincts coexistent :

- **Côté serveur (Node.js, dans le terminal) :** Exécute les Route API (`app/api/`), les Server Components (sans `"use client"`), lit `.env.local`, accède au système de fichiers. Le navigateur ne voit jamais ce code.
- **Côté client (navigateur) :** Exécute les composants avec `"use client"` (comme `ContactForm.tsx`). C'est du JavaScript envoyé au navigateur.

**Indicateur pratique :** `"use client"` en haut du fichier → navigateur. Dans `app/api/` ou composant sans cette directive → serveur.

**Pourquoi c'est important pour la sécurité :** mettre un secret (App Password) dans un composant `"use client"` l'exposerait dans le code JavaScript envoyé à tous les navigateurs. Dans une Route API, il reste sur le serveur.

### GET vs POST

- **GET** : conçu pour *récupérer* des données. Paramètres visibles dans l'URL, loggés par les serveurs intermédiaires, mis en cache, déclenchable par un simple lien. → Lecture seulement.
- **POST** : conçu pour *envoyer* des données. Données dans le corps de la requête (pas dans l'URL), non mis en cache, nécessite une action délibérée. → Action, modification.

Envoyer un email est une action → POST. Accepter GET permettrait à un bot de déclencher des envois d'emails en visitant une URL.

### App Password Google

L'App Password est un mot de passe de 16 caractères généré par Google qui permet à une application externe (Nodemailer) de s'authentifier auprès de Gmail sans utiliser le vrai mot de passe du compte.

- Nécessite la validation en 2 étapes activée sur le compte Google
- Ne donne accès qu'à la fonctionnalité d'envoi SMTP, pas au compte entier
- Révocable à tout moment sans changer le vrai mot de passe
- Généré dans : Compte Google → Sécurité → Validation en 2 étapes → Mots de passe des applications

### Variables d'environnement (`.env.local`)

Next.js lit `.env.local` au démarrage et expose les valeurs via `process.env.NOM_DE_LA_VARIABLE` dans le code serveur. Ce fichier :
- N'est jamais envoyé au navigateur
- N'est jamais commité sur GitHub (`.gitignore`)
- Doit être recréé manuellement sur chaque nouvelle machine ou serveur de déploiement

### Email header injection

Attaque qui consiste à insérer des sauts de ligne (`\r\n`) dans les champs d'un formulaire pour manipuler les en-têtes d'un email (ajouter des destinataires, modifier l'expéditeur, etc.). Contremesure : supprimer tous les `\r\n` des champs avant de les utiliser dans l'email.

### Honeypot anti-spam

Champ de formulaire rendu invisible aux utilisateurs réels (via CSS `opacity-0`, `pointer-events-none`, `aria-hidden`). Les bots de spam qui remplissent automatiquement tous les champs vont le remplir. Si ce champ contient une valeur → soumission ignorée silencieusement (on répond quand même 200 pour ne pas signaler au bot qu'il a été détecté).
